Lesson 01: Metric Definitions and Business Questions
Original fictional case: Analyst Mei and product lead Rafael compare September figures for the same 2,000 eligible users, using UTC calendar boundaries and excluding internal and test accounts. One report counts 1,200 distinct users with a successful login. Another counts 900 distinct users with a completed transaction. All 900 are within the login group. Both queries match their stated definitions. The business question is how many eligible users completed a transaction, not how many signed in. The team must choose an accurate label and rate.
Language workshop: Two active-user totals, two different events
Communication goal: Reconcile apparently conflicting metrics by stating the event, distinct entity, window, and denominator.
Language guidance: 900/2,000 is 45% of eligible users. 900/1,200 is 75% of users who logged in. Both calculations are valid for their stated bases, but only the first answers the supplied eligible-user question.
Useful expressions (preserve the supplied facts): "Are we measuring sign-in or completed transactions?" / "Each user is counted once." / "The qualifying event is a completed transaction." / "Use the September calendar month in UTC." / "Both measures exclude internal and test accounts." / "Both queries match their own definitions." / "The reports use different activity events." / "Nine hundred users answer the transaction question." / "The eligible population is 2,000 users." / "That is 45% of eligible users." / "Seventy-five percent uses logged-in users as its base." / "The transaction group is a subset of the login group." / "Call this transaction-active users." / "Keep the login measure under its own label." / "The metric owner should approve the shared definition." / "We need consistent meaning, not an artificial match between different events."
Vocabulary: metric: A defined quantitative measure. / business question: The decision-relevant question an analysis is meant to answer. / metric definition: Rules specifying exactly how a measure is calculated. / qualifying event: An action meeting the condition for inclusion. / distinct user: A unique user counted once under a defined identity rule. / event count: The number of recorded qualifying occurrences. / eligible population: The complete group allowed into the measure's base. / denominator: The total used as the base of a rate. / numerator: The counted outcome placed over the base of a rate. / reporting window: The time period included in a measure. / calendar month: A month bounded by the adopted calendar and time zone. / time zone: The time reference used to assign event dates. / exclusion rule: A condition removing records from the measure. / internal account: An account belonging to the organization's own personnel or systems. / test account: An account used for testing rather than genuine activity. / deduplication: Removing repeated representations of the same counted entity. / identity resolution: Connecting records that refer to the same entity. / active user: A user meeting a specified activity definition. / login-based activity: Activity defined by a qualifying sign-in. / transaction-based activity: Activity defined by a qualifying transaction. / subset: A group entirely contained within another group. / metric owner: The role accountable for a measure's definition and use. / semantic layer: Shared definitions connecting data to business meaning. / reconciliation: Explaining and resolving differences between reported figures.
Speaking task: Read turns 1-10. Stress qualifying event and denominator as separate choices. Switch roles for turns 11-20. Keep the subset relationship clear when rejecting addition. Check the transfer. Read 40% and 50% with their different population bases.
Partner: Mei: Data analyst / Rafael: Product lead
Guided response task: Select supplied answers for the dialogue gaps. Check the explanations, then read the completed exchange aloud; no original writing is required.
Optional second-round challenge: A month has 1,000 eligible users, 800 distinct login users, and 400 distinct transacting users, all within the login group. The question asks for transaction activity among all eligible users.
Model for comparison AFTER my attempt, not a response to give me first: Rafael: Who signs off if the transaction event changes next month? I do not want the same label to hide a new definition.
Mei: Assign a metric owner and record the approved version. That gives both teams a place to resolve changes before comparing totals that no longer mean the same thing.
Rafael: My summary will be nine hundred transaction-active users, forty-five percent of two thousand eligible users, September UTC. The login measure remains separately labeled.
Mei: That completes the reconciliation. We have preserved both correct calculations, selected the measure that answers the decision, and removed the ambiguity that created the apparent conflict.

Lesson 02: Data Quality and Trust
Original fictional case: Reporting analyst Asha reviews a dashboard with operations manager Tomas on Wednesday at 09:00 UTC. The dashboard refresh completed, and the orders source is verified complete through Tuesday 23:59 UTC. The refunds source is verified complete only through Monday 23:59 UTC because its next delivery is delayed. A Monday-Tuesday net-order-value figure subtracts available refunds from orders, so the periods are misaligned. Asha can publish a verified Monday-only comparison; Tuesday refunds are unknown, not confirmed zero. No delivery time for the missing source is confirmed.
Language workshop: Refreshed today, complete only through Monday

Lesson 05: SQL, Models, and Transformation Logic
Original fictional case: Analytics engineer Lina reviews a report with analyst Owen. The complete teaching dataset has two orders: O1 is $100 and O2 is $100. Payment rows are O1: $60 and $40; O2: $100. Joining orders to payments on order ID creates three rows. Summing the repeated order amount then gives $300, although total order value is $200. SUM(DISTINCT order_amount) gives $100 because the two legitimate orders share an amount. Lina proposes aggregating payments to one row per order before joining, with key and total checks.
Language workshop: The join adds rows, not order value
Communication goal: Explain row grain and join multiplicity, diagnose a duplicated aggregate, and reject a misleading distinct-value fix.
Language guidance: The joined order amounts are 100, 100, and 100: O1 appears twice because it has two payments. The correct order total is 200. The payment amounts themselves are 60, 40, and 100, also totaling 200 for this dataset.
Useful expressions (preserve the supplied facts): "What does one row represent before the join?" / "The tables match on order ID." / "O1 has two payment rows." / "The order row is repeated for each matching payment." / "The extra row is not an extra order." / "Summing joined order amounts produces $300." / "The order-level total is $200." / "Distinct amounts do not mean distinct orders." / "Both legitimate orders have an amount of $100." / "Aggregate payments to one row per order before joining." / "Check uniqueness of order ID in the summarized payments." / "The intended order population must survive the join." / "Reconcile the repaired output to the source order total." / "Order value and payment value are different measures." / "Define how orders without payments are represented." / "Fix the grain and verify the result before republishing."
Vocabulary: SQL: Structured Query Language, used to query relational data. / row grain: What one row represents in a dataset. / primary key: A non-null column or set of columns uniquely identifying each row. / foreign key: A column or set of columns constrained to reference a key in a table. / join key: The field or fields used to match tables. / join cardinality: The relationship in match counts between joined entities. / one-to-many relationship: One entity matching multiple related records. / fanout: Multiplication of rows caused by multiple join matches. / aggregation: Combining records into summary values. / pre-aggregation: Summarizing data before another transformation or join. / GROUP BY: SQL grouping of rows for aggregate calculations. / SUM: An aggregate that adds non-null numeric values. / DISTINCT: SQL removal of duplicate values or rows in its specified scope. / COUNT: An aggregate that counts rows or non-null expressions. / inner join: A join returning matching combinations from both sides. / left join: A join retaining left rows even without a right match. / null handling: Rules for processing missing or unknown values. / filter: A condition selecting which records remain. / CTE: Common table expression, a named query expression. / data model: A representation of entities, relationships, and measures. / fact table: A table storing business events or measurements at a defined grain. / dimension table: A table holding descriptive attributes for analysis. / reconciliation total: A reference total used to verify transformed output. / uniqueness test: A check that a defined key has no duplicates.

Language workshop: A positive estimate is not the rollout rule

Language guidance: The point estimate is +1.2 points, but the interval runs from -0.4 to +2.8. It includes zero and values below the practical threshold. Under the supplied rule, a passing guardrail cannot compensate for a failing lower bound.
