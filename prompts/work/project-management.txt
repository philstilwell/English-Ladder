5. Finish with two new four-choice collocation questions for later review, with a clearly separate answer key. Do not claim to schedule a reminder.

Lesson 01: Project Charter and Scope Definition
Original fictional case: Sponsor Greg requests a dashboard in four weeks, but the initial brief does not identify users, decisions, or exclusions. In a planning meeting with project manager Elena, he proposes a first release for operations leads doing weekly queue triage: overdue-item visibility and an export. Automated work allocation would be excluded. Data access and acceptance criteria remain unconfirmed, and no scope baseline is approved. Elena must turn the request into a reviewable definition without promising the four-week target.
Language workshop: A dashboard is not yet a defined project
Communication goal: Clarify the users, decisions, boundaries, and acceptance basis behind a sponsor request before treating a target date as a commitment.
Language guidance: A dashboard is an output; improved queue decisions would be an intended outcome. The proposed users and exclusions narrow the request, but they do not confirm access, acceptance, or schedule feasibility. Four weeks remains a target until supported and authorized.
Useful expressions (preserve the supplied facts): Which decision should the dashboard help users make? / The proposed first users are operations leads. / They will use it for weekly queue triage. / The first release would show overdue items and provide an export. / Automated allocation is outside the proposed first release. / A delivered screen is not itself evidence of better queue decisions. / Four weeks is the requested target, not yet a delivery commitment. / We still need to confirm access to the source data. / What evidence will show that the first release meets the agreed need? / Who is authorized to accept the defined output? / Record the data-access assumption until it is verified. / A useful future feature is not automatically part of this release. / Replace looks good with a checkable acceptance condition. / These are proposed boundaries pending review. / Link the requirements to the scope and acceptance evidence. / Confirm users, decision use, inclusions, exclusions, and approval route.
Vocabulary: project charter: A document formally establishing a project and its high-level authority and purpose. / project sponsor: The person accountable for sponsorship and relevant business decisions. / business need: The problem or opportunity the work is intended to address. / business case: The justification for the proposed investment and expected value. / project objective: A specific result the project is intended to achieve. / deliverable: A defined output to be produced by the project. / outcome: A change or result enabled by using the project's outputs. / benefit: A measurable improvement of value from the change. / scope statement: A description of the work and boundaries included in the project. / scope baseline: The approved scope reference used to manage and assess changes. / in scope: Included within the defined project boundary. / out of scope: Excluded from the defined project boundary. / assumption: A premise used for planning that needs appropriate validation or monitoring. / constraint: A limit within which the project must operate. / requirement: A defined need or condition the solution must satisfy. / acceptance criterion: A condition used to decide whether an output is acceptable. / stakeholder: A person or group affected by or able to affect the project. / end user: A person who will use the delivered capability. / decision use: The decision or action a delivered information product supports. / work breakdown structure: A hierarchical division of project work into manageable components, abbreviated WBS. / work package: A defined unit of work that can be assigned and managed. / requirements traceability: Links connecting needs, requirements, work, and evidence. / success measure: A defined indicator used to assess the intended result. / scope approval: Authorization of the stated project boundaries and work.
Speaking task: Read the corrected charter dialogue. Name operations leads, weekly triage, overdue-item visibility, and the export before stating the excluded automation. Switch roles for turns 11-20. Keep the four-week target and data-access assumption separate from approval. Complete and check the transfer. Read the proposed export boundary without adding automated allocation or a delivery commitment.
Partner: Greg: Project sponsor / Elena: Project manager
Guided response task: Select supplied answers for the dialogue gaps. Check the explanations, then read the completed exchange aloud; no original writing is required.
Optional second-round challenge: A proposed first release includes a weekly export for operations leads. Automated allocation is excluded. Data access is unconfirmed, and the target date has not been approved.
Model for comparison AFTER my attempt, not a response to give me first: Greg: We should keep the requirements connected to the reason for the project. Otherwise an attractive feature may distract us from the weekly triage need.
Elena: Use requirements traceability to preserve those connections. The record should show why the work exists, how it is checked, and whether it belongs in this release.
Greg: Good. Please bring the definition and unresolved decisions to the review. I will not announce the date or the wider automation feature as approved today.
Elena: Then we can seek scope approval on a clear basis. The immediate result is a reviewable proposal, not a promise built from a product name and a target alone.
