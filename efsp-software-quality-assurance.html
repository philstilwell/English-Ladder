01Agreeing the expected resultAsk what makes the result correct · 45-60 minutes+

Your goal

Resolve a missing expectation before assigning a test verdict.

A Read the situation

A moment at work

A fictional booking feature says cancellations are allowed 'within 24 hours.' One example allows cancellation exactly 24 hours before the event; another rejects it. Time-zone handling is outside this exercise. The requirement owner can clarify the equality case.

Before you look at the model: what is confirmed, what is missing, and who needs a response?

B Find the words

Vocabulary for this lesson

test oracle
A source or method used to determine whether an observed software result is acceptable or correct.
acceptance criterion
A specific condition that a feature or change must satisfy to be accepted by the relevant stakeholders.
expected result
The outcome a test is meant to check against a stated requirement or other justified basis.
ambiguity
Wording or evidence that permits more than one plausible interpretation of intended behavior.

Useful word combinations

  • establish the test oracle: identify a credible basis for judging an outcome
  • clarify a boundary rule: settle what happens at a stated limit
  • compare expected and actual results: distinguish the specified outcome from the observation
  • resolve conflicting examples: determine which source expresses the intended behavior

C Notice the language

Ask what makes the result correct

A test oracle is the basis for judging the result, not necessarily another program. When wording and examples conflict, state the precise input whose outcome is uncertain and ask the responsible person to settle it.

  • For input ___, source A expects ___ while source B expects ___.
  • Which source should govern the equality case?
  • The observed result is ___; the expected result is still ___.

Improve this: "The test failed because I expected the other result."

See a clearer version

The examples disagree at exactly twenty-four hours; we need the intended equality outcome before assigning a verdict.

The revision distinguishes personal expectation from an agreed basis for evaluating the behavior.

D Check your understanding

Two short language checks

These language patterns recur across courses so you can retrieve and reuse them.

1. Tester: The examples disagree at exactly twenty-four hours.
Requirement owner: We need to clarify the ____ case before you judge it.

Answer and explanations

Answer: A. boundary

  1. A. boundary Correct. Equality at the stated limit is the boundary question.
  2. B. time-zone Time-zone handling is explicitly outside this case; the conflict concerns equality.
  3. C. state-transition No workflow-state transition is the disputed condition here.
  4. D. formatting The examples disagree about permission, not the appearance of a displayed value.
2. Developer: Can you report what happened despite the ambiguity?
Tester: Yes; I can report the observation, but the ____ remains unsettled.

Answer and explanations

Answer: D. expected result

  1. A. actual output The actual output is the observation already available.
  2. B. build identifier The build identity is not the disputed issue.
  3. C. execution time No uncertainty about execution time is supplied.
  4. D. expected result Correct. Conflicting examples leave the intended outcome unresolved.

E Conversations

Three conversations at work

Original fictional training conversations. Each line is one speaking turn.

1. Exactly twenty-four hours before the event

A fictional tester and requirement owner clarify conflicting cancellation examples.

  1. Tester: Our cancellation examples disagree at exactly twenty-four hours before the event. Which outcome is intended?
  2. Requirement owner: That equality case should allow cancellation. Please use that as the confirmed outcome.
  3. Tester: Thank you. The phrase within twenty-four hours didn't clearly distinguish equality from either neighboring case.
  4. Requirement owner: Agreed. We should state the equality rule explicitly rather than expect the examples to explain themselves.
  5. Tester: Then allowed cancellation at exactly twenty-four hours becomes the acceptance criterion for this case.
  6. Requirement owner: Yes. Don't infer the rest of the time-window rule from that single clarification, though.
  7. Tester: I won't. The remaining wording and time-zone handling still need separate clarification.
  8. Requirement owner: Can you report the observed result separately from the expectation we just agreed?
  9. Tester: Yes. I'll compare the recorded outcome with allowed cancellation, using this clarification as the test oracle.
  10. Requirement owner: That settles the equality verdict's basis without pretending we resolved every timing question.
2. The old screen is not automatically the rule

A fictional tester challenges a reference screenshot used as the only expectation.

  1. Developer: The new screen differs from the old screenshot. Shouldn't that automatically make the test fail?
  2. Tester: Which part differs, and is the screenshot an approved requirement or only historical evidence?
  3. Developer: The label now says inactive rather than closed. The screenshot came from last year's build.
  4. Tester: Then it shows previous behavior, but doesn't establish whether the new wording is wrong.
  5. Developer: The updated requirement says inactive for accounts that can be reopened. This account fits that condition.
  6. Tester: That gives us a stronger oracle for this label than the older screenshot.
  7. Developer: So the observed inactive label agrees with the current acceptance criterion for this account.
  8. Tester: Yes. We can record that result while noting why the historical comparison initially looked different.
  9. Developer: I'll identify the screenshot as superseded reference material instead of making it the expected result.
  10. Tester: And we'll avoid calling an intended change a defect solely because it looks unfamiliar.
3. A reference calculator disagrees with the specification

Fictional testers compare two sources for a rounded display value.

  1. Tester: The reference calculator rounds at each step, but the specification rounds only the final display value.
  2. Requirement owner: Which input exposes the difference? We need a concrete case rather than two general descriptions.
  3. Tester: The inputs are 0.044 and 0.044. Rounding each to two decimals totals 0.08; rounding only their sum gives 0.09.
  4. Requirement owner: The current display requirement governs this feature: intermediate values retain precision, and only the display rounds.
  5. Tester: Then the calculator isn't a reliable oracle for that example unless its settings match the requirement.
  6. Requirement owner: Correct. Its result may be valid for another rule, but not the rule we're evaluating here.
  7. Tester: I'll retain both outputs and explain the mismatched rounding basis in the test discussion.
  8. Requirement owner: Please avoid saying the calculator is universally wrong. We have identified a difference in intended behavior.
  9. Tester: Understood. For this test, the final-display rule supplies the expected result.
  10. Requirement owner: Unresolved arithmetic details should come back for clarification, not be guessed.

Scenario 2 · The warning text says soon

A fictional storage screen warns that a file will expire 'soon.' One acceptance example expects three days remaining; another expects seven. The requirement owner can choose three days for the warning boundary in this exercise.

Role A: Tester: request a measurable warning condition rather than inventing a meaning for soon.

Role B: Requirement owner: confirm three days remaining as the intended warning point and identify the seven-day example as outdated.

Possible opening: “Which remaining-time condition should trigger this warning: three days or seven?”

Success checks
  • Identify the conflicting examples.
  • Confirm the three-day criterion explicitly.
  • Separate outdated evidence from the current expectation.
Add a complication

A colleague says either is acceptable because soon is subjective.

Studying alone? Speak both roles aloud. For each scenario, prepare for two minutes, speak for one minute, then answer a follow-up. Switch roles and repeat using fewer notes. Use only the supplied facts; identify missing information instead of inventing it.

02Making a failure reproducibleRequest a comparable reproduction · 45-60 minutes+

Your goal

Supply the starting state, actions, and result needed to repeat an observation.

A Read the situation

A moment at work

A fictional tester sees an export omit the last selected item in build Q12, using a saved selection of three items. A developer's one-item attempt succeeds. The tester reproduced the omission twice in two attempts; no other build or selection size has been checked.

Before you look at the model: what is confirmed, what is missing, and who needs a response?

B Find the words

Vocabulary for this lesson

precondition
A required state or condition that must hold before a test's actions begin.
reproduction steps
An ordered description of actions used to make an observed behavior occur again.
test environment
The software, configuration, data, and other conditions in which testing is performed.
actual result
The behavior or output observed during a particular test execution.

Useful word combinations

  • state the starting state: describe conditions that must hold before the actions
  • identify the tested build: specify the version that produced the observation
  • preserve the failing sequence: retain the order of actions that led to the failure
  • report reproduction frequency: state how often the behavior occurred in recorded attempts

C Notice the language

Request a comparable reproduction

A clear report distinguishes preconditions from steps and actual behavior from expected behavior. Two failures in two attempts are a bounded observation, not a claim that every user always fails.

  • Start with ___ on build ___.
  • After ___, I observed ___ in ___ attempts.
  • Your attempt differs in ___; could we align that condition?

Improve this: "Export is broken. Try it again."

See a clearer version

On Q12, export the saved three-item selection; the final selected item was absent in both recorded attempts.

The revised request gives a repeatable context and limits the frequency claim to the evidence.

D Check your understanding

Two short language checks

These language patterns recur across courses so you can retrieve and reuse them.

1. Developer: My one-item export succeeds.
Tester: Please repeat it with ____ so the starting condition matches my report.

Answer and explanations

Answer: D. the saved three-item selection

  1. A. a later build A later build would introduce another difference.
  2. B. a different output type A different output type would change the tested workflow.
  3. C. an empty selection An empty selection does not match the failing condition.
  4. D. the saved three-item selection Correct. This matches the supplied failing selection.
2. Lead: How often has it happened in your checks?
Tester: It occurred ____; other selections are untested.

Answer and explanations

Answer: C. in both recorded attempts

  1. A. on every build Only Q12 has been checked in the case.
  2. B. in no comparable attempts There are two recorded matching failures.
  3. C. in both recorded attempts Correct. This reports the two observed attempts without generalizing.
  4. D. for every customer Customer-wide frequency has not been investigated here.

E Conversations

Three conversations at work

Original fictional training conversations. Each line is one speaking turn.

1. Three selected items, not one

A fictional tester requests a comparable reproduction of the Q12 export omission.

  1. Tester: My Q12 export omitted the final item from a saved three-item selection in both attempts.
  2. Developer: My one-item selection exported correctly. What starting condition should I change to match yours?
  3. Tester: Use the saved three-item selection, then export without changing its order or output type.
  4. Developer: Can you provide that selection? A screenshot alone doesn't show how those items were chosen.
  5. Tester: Yes. It is attached with the reproduction steps and the expected three exported items.
  6. Developer: Then my passing attempt doesn't contradict yours; the precondition differs in selection size and state.
  7. Tester: Exactly. We haven't tested every size or another build, so the claim remains bounded.
  8. Developer: I'll repeat the stated sequence on Q12 and compare actual results before discussing a cause.
  9. Tester: Please retain the last item's reference in your output so we can identify the omission precisely.
  10. Developer: I have the matching fixture and steps now. The original report is specific enough to reproduce.
2. The report omitted the starting account state

A fictional tester and developer clarify why a saved filter isn't visible.

  1. Developer: I followed your steps, but the filter appeared normally. Was your account new or previously configured?

Your goal

Justify a small test selection using the rule's actual distinctions.

A Read the situation

A moment at work

A fictional form accepts whole-number quantities from 1 through 20 inclusive and rejects values outside that range. A proposed test set contains 5, 10, and 15 only. Decimal handling is unspecified and outside the stated whole-number rule.

Before you look at the model: what is confirmed, what is missing, and who needs a response?

B Find the words

Vocabulary for this lesson

equivalence partition
A group of inputs or states expected to receive similar treatment for the rule being tested.
boundary value
An input at or near a limit where specified behavior may change.
decision table
A structured representation connecting combinations of conditions with their expected actions or outcomes.
negative test
A test examining behavior under invalid inputs, disallowed actions, or other specified exceptional conditions.

Useful word combinations

  • cover both sides of a boundary: examine values immediately inside and outside a limit
  • choose a representative input: select a value from a justified behavior group
  • exercise a rule combination: check a specified combination of conditions
  • check rejection behavior: observe how the system handles disallowed input

C Notice the language

Explain why another middle value adds little

Partitioning groups inputs expected to receive similar treatment. Boundary cases probe transitions between groups. Neither approach means one successful sample proves every value behaves correctly; explain the selection and its limits.

  • These values all represent ___, while ___ is missing.
  • At ___ the expected result changes from ___ to ___.
  • The requirement covers ___ but does not specify ___.

Improve this: "We tested three quantities, so quantity validation is covered."

See a clearer version

The three tests cover accepted interior values; the minimum, maximum, and neighboring rejected values remain unchecked.

The revised statement describes the kind of coverage rather than substituting a test count for it.

These language patterns recur across courses so you can retrieve and reuse them.

Tester: ____ exercises that rejected whole-number neighbor.

Answer and explanations

Answer: C. Twenty-one

  1. A. Twenty Twenty is the included upper boundary, not outside it.
  2. B. Ten Ten is an accepted interior value.
  3. C. Twenty-one Correct. Twenty-one is the next whole number above the limit.
  4. D. Nineteen Nineteen is inside the accepted range.
2. Developer: The rule covers whole numbers. Should 1.5 pass?
Tester: Decimal handling is ____, so we need a separate expectation.

Answer and explanations

Answer: B. unspecified

  1. A. confirmed by the accepted interior samples Accepted whole-number samples do not settle the missing decimal rule.
  2. B. unspecified Correct. The supplied rule does not settle decimal inputs.
  3. C. covered by the endpoint tests Whole-number endpoint tests do not establish an expectation for decimal handling.

Your goal

Explain why broad initial checks do not replace targeted regression evidence.

A Read the situation

A moment at work

A fictional account update passes a smoke test covering sign-in and opening the account page. The update changes a formatter used by both account-save and the existing export path; neither path has been tested. One hour is available for further checking; no claim of full coverage is justified.

Before you look at the model: what is confirmed, what is missing, and who needs a response?

B Find the words

Vocabulary for this lesson

test coverage
The extent to which tests address a stated set of requirements, code structures, risks, or other defined items.
traceability
Explicit links connecting requirements, tests, results, and related defects or other supporting records.
regression testing
Testing for unintended effects of changes on existing behavior, including behavior outside the changed area.
smoke test
A limited initial check of important basic functions used to assess whether further testing is practical.

Useful word combinations

  • map a check to a requirement: show which stated behavior a test examines
  • identify an untested path: name a workflow not exercised by the evidence
  • prioritize by change risk: focus limited checking on plausible consequences of a change
  • distinguish breadth from depth: separate many touched areas from thorough examination of each

C Notice the language

Compare checks by the risk they address

Coverage needs a named basis, such as requirements, paths, or configurations. A large test count does not establish that the changed behavior was checked. Describe the selection's rationale and the work left outside it.

  • This check covers ___, whereas the change affects ___.
  • Because ___ is shared, ___ is a relevant regression concern.
  • Within the available time, I propose ___; ___ would remain untested.

Improve this: "The smoke test passed, so the change is covered."

See a clearer version

Sign-in and page opening passed; save and the shared formatter's export path remain untested.

The revision attaches the passing result to the behaviors actually checked.

1. Lead: Why test export when only save was changed?

Answer and explanations

Answer: B. shared formatter

  1. A. test fixture A test fixture supplies starting data, not the shared formatting behavior identified here.
  2. B. shared formatter Correct. The common formatter connects the changed and existing paths.
  3. C. permission lookup The case identifies no changed permission lookup shared by these paths.
  4. D. input validator No shared input-validator change is supplied in this case.
2. Manager: We ran fifty tests. What coverage can we claim?
Tester: We need to state ____ before the count has a useful coverage meaning.

Answer and explanations

Answer: A. what behaviors those tests exercise

  1. A. what behaviors those tests exercise Correct. Coverage requires a stated basis, not just a count.
  2. B. how many times each check was repeated Repetition counts do not identify which behaviors are covered.
  3. C. whether the tests passed on an older build An older passing result does not define the checks' coverage.
  4. D. how long the full run took Execution duration does not establish the scope of checked behavior.

05Investigating inconsistent automated resultsExplain an unstable result without dismissing it · 45-60 minutes+

Your goal

Use run context to distinguish a supported test problem from an unsupported product verdict.

A Read the situation

A moment at work

In a fictional automated suite on build T8, a search check fails after a cleanup check but passes when run alone. The cleanup check removes a shared sample record that the search check expects. No code change occurs between these observations.

Before you look at the model: what is confirmed, what is missing, and who needs a response?

B Find the words

Vocabulary for this lesson

flaky test
A test producing inconsistent outcomes across repeated runs without an intended relevant change to the tested software.
test fixture
The data and setup needed to give a test its intended starting conditions.
test isolation
Keeping a test's relevant state and outcome independent of unintended effects from other tests.
false positive
A test result that incorrectly signals a product problem when the claimed problem is not present.

Useful word combinations

  • retain the first failure: preserve evidence even when a rerun passes
  • reset the starting data: restore the stated fixture before an independent attempt
  • separate product and test causes: distinguish a software defect from a check's own problem
  • compare isolated and grouped runs: examine whether neighboring tests affect the result

C Notice the language

Explain an unstable result without dismissing it

An inconsistent test result still deserves investigation. Passing on rerun doesn't erase the earlier evidence. Once a fixture interaction is identified, limit the conclusion to that interaction rather than treating all failures as noise.

  • The same build passes when ___ but fails when ___.
  • The fixture difference is ___, which supports ___.
  • That explains this result pattern, not every possible ___.

Improve this: "It's flaky, so ignore the red result."

See a clearer version

The check depends on a record removed by an earlier test; its starting state is not isolated.

The revision names the evidenced interaction instead of using flakiness as a dismissal.

D Check your understanding

Two short language checks

These language patterns recur across courses so you can retrieve and reuse them.

1. Developer: Why does the search check fail after cleanup?
Tester: Its required sample record has been ____, so the fixture differs.

Answer and explanations

Answer: A. removed

  1. A. removed Correct. Cleanup removes the record that search expects.
  2. B. altered by search The evidence identifies cleanup removal, not a search operation altering the record.
  3. C. duplicated during setup No duplicate record is reported; the required record is absent.
  4. D. hidden by a filter A filtering explanation does not match the confirmed removal by cleanup.
2. Lead: Does the passing rerun prove a product fix?
Tester: No; ____ changed between the observations.

Answer and explanations

Answer: D. the test's starting context

  1. A. the release contract No changed release contract is supplied.

  3. C. the product requirement No requirement change explains these observations.

08Giving a release-evidence handoverSeparate evidence from the release decision · 45-60 minutes+

Your goal

Hand over accurate test status and remaining uncertainty to the named decision owner.

A Read the situation

A moment at work

A fictional candidate Q20 has ten planned checks: seven passed, one failed, and two blocked by unavailable sample data. The agreed exit criterion requires all critical-path checks executed and reviewed; one blocked check is critical. Mara owns the release decision, which has not been made.

Before you look at the model: what is confirmed, what is missing, and who needs a response?

B Find the words

Vocabulary for this lesson

test summary
A report of testing scope, execution results, limitations, and relevant remaining concerns.
residual risk
The possibility of adverse outcomes that remains after the checks and other measures already taken.
exit criterion
An agreed condition used to determine whether a testing activity can be considered complete.
blocked test
A test that cannot be completed as intended because a required condition, resource, or dependency is unavailable.

Useful word combinations

  • report by result category: separate passed, failed, blocked, and unexecuted checks
  • state the evidence cutoff: identify the latest build and time included in a summary
  • hand over an unresolved risk: transfer an open concern with its evidence and owner
  • assess an exit criterion: compare actual evidence with an agreed completion condition

C Notice the language

Separate evidence from the release decision

Blocked is not passed or failed behavior: the intended check could not be completed. A pass percentage needs a clear denominator, and outstanding critical evidence matters even when most executed tests pass.

  • Of ___ planned checks, ___ passed, ___ failed, and ___ were blocked.
  • The agreed criterion remains unmet because ___.
  • ___ owns the decision; this summary establishes ___.

Improve this: "Almost everything passed, so quality assurance has approved release."

See a clearer version

Seven of ten planned checks passed; one failed and two were blocked. A critical blocked check leaves the exit criterion unmet.

The revision gives the full result distribution and avoids inventing a release decision.

D Check your understanding

Two short language checks

These language patterns recur across courses so you can retrieve and reuse them.

1. Mara: Did the two data-blocked checks fail the product?
Tester: No; their intended behavior was ____ because the required data was unavailable.

Answer and explanations

Answer: B. not evaluated

  1. A. successfully reviewed Review of the intended result cannot be claimed here.
  2. B. not evaluated Correct. Blocked execution leaves the intended behavior unevaluated.
  3. C. confirmed incorrect A blocked test does not establish a product failure.
  4. D. proven correct Missing execution cannot establish a passing behavior.
2. Lead: Has the critical-path exit criterion been met?
Tester: No; one critical check remains ____.

Answer and explanations

Answer: A. blocked

  1. A. blocked Correct. The blocked critical check prevents the required execution and review.
  2. B. passed The critical check has not passed; its required data is unavailable.
  3. C. failed No evaluated failing result exists for this blocked critical check.
  4. D. not yet selected The critical check is already selected in the ten-check plan.
