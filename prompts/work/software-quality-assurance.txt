Tester Maya and requirement owner Dev review the conflict. The equality case has not been settled. Time-zone handling is outside this discussion. Maya needs an agreed expected result before using a test to declare this exact boundary behavior correct or defective.
Language workshop: Exactly twenty-four hours: accept or reject?
Communication goal: Expose contradictory examples and obtain a clear equality rule without inventing a missing requirement.
Language guidance: The exact twenty-four-hour case has two conflicting expected outcomes. Neither the word within nor the current implementation resolves that conflict by itself. Request an explicit accept-or-reject decision for equality.
Useful expressions (preserve the supplied facts): The two examples disagree at exactly twenty-four hours. / One example allows the cancellation. / The other rejects the same case. / Should equality be accepted or rejected? / My interpretation is not yet an agreed rule. / Can the requirement owner clarify this point? / Current behavior does not settle intended behavior. / We need one expected result for this input. / I am asking about the endpoint itself. / Time-zone handling is outside this discussion. / Please update the conflicting example after the decision. / Link the test to the clarified requirement. / I cannot make a justified pass/fail judgment on this case yet. / The equality rule remains unresolved. / This is a clarification request, not a chosen outcome. / Record the intended result before finalizing the test expectation.
Vocabulary: requirement: Statement of behavior or capability the product should provide. / expected result: Outcome a test should produce under the agreed rule. / actual result: Outcome observed when the test is executed. / acceptance criterion: Condition used to judge whether a requirement is met. / ambiguity: Wording that permits more than one interpretation. / contradiction: Two statements that cannot both hold for the same case. / boundary: Point where an applicable rule or outcome changes. / equality case: Input exactly equal to the specified threshold. / inclusive limit: Limit that includes the endpoint itself. / exclusive limit: Limit that excludes the endpoint itself. / threshold: Value at which a rule changes or applies. / test oracle: Reference used to decide the expected outcome. / test basis: Information from which tests and expectations are derived. / Boolean condition: Condition with a true or false value. / business rule: Product behavior specified for a business purpose. / requirement owner: Person responsible for clarifying the relevant requirement. / decision record: Traceable statement of an agreed decision. / assumption: Belief used without current confirmation. / precondition: State required before a test action is performed. / postcondition: State expected after the relevant action. / traceability: Ability to link a test or result to its supporting requirement. / scope boundary: Limit on topics or behavior covered by the work. / pass/fail judgment: Conclusion comparing observed behavior with an agreed expectation. / clarification request: Specific question seeking missing or inconsistent information.

Lesson 02: Making a failure reproducible
Original fictional case: On fictional build Q12, tester Hana exports a saved selection of three items. The output omits the last selected item. She observes the omission in two attempts out of two. Developer Joel exports one item successfully. No other build or selection size has been checked. They compare conditions and prepare a handoff using the saved three-item selection, the export action, and the observed output without claiming every export fails.
Language workshop: Three selected, two exported, twice
Communication goal: Give a reproducible defect report and explain why a successful attempt with different input does not disprove it.
