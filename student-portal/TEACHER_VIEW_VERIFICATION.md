# Required Teacher view verification

Owner authorization, November 13, 2026: perform this check automatically after every successful nightly lesson publication. It uses the existing Codex allowance, the saved Mac Keychain administrator credential and the existing browser tools, with no additional AI service charges. Keep the single 23:35 America/New_York automation and all publication safeguards.

## Identify and track the exact publication

Before publication, create a mode-600 receipt in ignored `student-portal/private/codex-nightly/` named `<studentId>-<sessionId>-teacher-view.json`. Record `studentId`, `sessionId`, the approved `recordsHash`, paths to the private prepared/approved/publish receipts, `status: "pending"`, and creation time. Keep credentials, transcript text and student answers out of this receipt. Only begin the browser check after the publication receipt and the handoff `verify` command confirm the session is saved. If publication did not succeed, this receipt does not authorize a retry of publication.

## Check through the visible browser interface

1. Use the supported browser/computer-use tools. Open `https://phil.englishladder.com/`, reuse its session or sign in with the Keychain item specified in CODEX_UPDATES.md. Open the exact student's account and record the current quiz status and visible attempt identifiers/results for comparison. Follow its **Open student site** link. Sign in separately on that host with the administrator credential if necessary. Confirm the correct student and the visible **Teacher view** banner. If the banner is absent, stop before answering anything; do not use a student session for testing.
2. Open **Overview → Feedback** and select the exact published session. Compare its date and title with the approved record using the prepared lesson time zone. Check that its summary, strengths, practice topics, vocabulary, practice tasks and next step render as authored, without missing text, errors or unusable layout. Expand every example answer. Check that next-step directions name sections and menu routes that actually exist. Inspect a screenshot as well as the page text; a server response alone cannot establish correct display.
3. Open **Overview → Quiz**. Match the quiz title, wording and source dates to the approved quiz for this publication. Check exactly seven questions, numbered 1–7, with all lettered choices and readable instructions. In confirmed Teacher view only, try one deliberately incorrect choice to check the retry explanation, then the correct choice. Check the correct answer and explanation for each of the seven questions against the approved record. Use the question navigation and completion/results controls. The deliberate first-choice error can reduce the preview score; do not mistake that expected result for a defect. Never switch to a student login or start a saved student attempt.
4. Refresh the administrator's quiz results and compare with the baseline. Confirm that the preview created no student attempt and changed no existing choices, result or saved progress. Investigate unexpected changes; do not overwrite or undo legitimate concurrent student work. A changed or unverifiable state cannot be marked as confirmed preservation.
5. Close only the temporary tabs/dialogs opened for this check. Preserve the owner's tabs and existing sign-in sessions. Clear transient credentials. Save a useful screenshot in the ignored private directory only when needed as evidence; never commit it or capture a password field containing a revealed credential.

## Record results and handle failures

- Set `status: "passed"` only when all checks pass. Include the verification time, exact feedback/quiz identity, `questionsChecked: 7`, and booleans for Teacher view, feedback, examples, choices, answer feedback, navigation, completion and unchanged student results. Include this result in the nightly publication report.
- For authentication, browser availability, missing content, wrong session/quiz, display, navigation or result-preservation failures, set `status: "failed"` with the failing step and a short non-secret explanation. Report the student, lesson date, what failed, whether publication itself succeeded, and any action the owner must take. Never describe a saved lesson as fully verified when the browser check failed.
- Allow at most one refresh/reopen retry for a transient browser or page-load failure in a run. Do not repeatedly attempt a rejected password or bypass browser restrictions. A failed check does not roll back, regenerate or republish the lesson, consume another authoring attempt, or block checks for other students.
- At the next nightly run, retry outstanding checks from these receipts once under the same browser retry bound, after confirming publication. Do not repeat passed checks unless the published records changed or the owner requests it. Keep unchanged unresolved failures in the private receipt; report a newly failed check, a changed blocker, or successful recovery. If a later quiz has replaced the target quiz and the exact earlier quiz is not available in Teacher view, record that limitation rather than checking the new quiz under the old session's receipt. Do not replace the current quiz to test an old one. Skip paused, deleted and ignored accounts and retain the reason privately.
