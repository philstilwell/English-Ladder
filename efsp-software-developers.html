01Clarifying interface contractsAsk about one ambiguous input · 45-60 minutes+

Your goal

Resolve an interface ambiguity using concrete input and outcome pairs.

A Read the situation

A moment at work

A fictional profile interface accepts an optional nickname. The current contract distinguishes an omitted nickname, which leaves it unchanged, from an empty string, which clears it. A proposed client sends null, whose meaning is unspecified.

Before you look at the model: what is confirmed, what is missing, and who needs a response?

B Find the words

Vocabulary for this lesson

interface contract
The specified inputs, outputs, errors, and behavior that callers and an implementation agree to rely on.
nullable field
A data field whose specified allowed values include null, distinct from whether the field may be omitted.
validation error
A reported failure because an input does not meet a stated rule or accepted format.
backward compatibility
The ability of a changed component to continue supporting behavior or inputs relied on by existing consumers.

Useful word combinations

  • define the accepted input: state which values an interface allows
  • distinguish absent from empty: separate an omitted field from a supplied empty value
  • preserve a caller's expectation: keep behavior an existing consumer relies on
  • reject an invalid value: return a specified failure for input outside the contract

C Notice the language

Ask about one ambiguous input

Explain the specified cases before asking about the gap. 'Optional' concerns whether a field must be present; 'nullable' concerns whether null is accepted. Neither automatically tells a caller what an empty string does.

  • For input ___, the contract specifies ___.
  • Does ___ mean ___, or should it be rejected?
  • That would change the behavior expected by ___.

Improve this: "Optional means you can send anything blank."

See a clearer version

Omission leaves the nickname unchanged; an empty string clears it. Null still needs a defined meaning.

The revision distinguishes three inputs instead of grouping them under the ambiguous word blank.

D Check your understanding

Two short language checks

These language patterns recur across courses so you can retrieve and reuse them.

1. Client developer: Can I send null to clear the nickname?
Service developer: The contract defines an empty string for clearing; null is ____.

Answer and explanations

Answer: B. unspecified

  1. A. deprecated Deprecated implies formerly supported behavior being phased out; that is not given.
  2. B. unspecified Correct. The meaning of null is not defined.
  3. C. equivalent Equivalence has not been agreed.
  4. D. required Required contradicts the optional field.
2. Reviewer: Does optional mean nullable?
Developer: No. Optional concerns presence, ____ nullable concerns accepting null.

Answer and explanations

Answer: A. whereas

  1. A. whereas Correct. Whereas contrasts different properties.
  2. B. therefore Therefore implies accepting null follows from optionality.
  3. C. because Because suggests null acceptance explains optionality.
  4. D. unless Unless introduces a condition rather than explaining the distinction.

E Conversations

Three conversations at work

Original fictional training conversations. Each line is one speaking turn.

1. What does null do to a nickname?

Two fictional developers resolve an unspecified input in the profile contract.

  1. Client developer: I want to clear a nickname. Can my client send null for that?
  2. Service developer: The contract specifies an empty string for clearing. Null doesn't currently have a defined meaning.
  3. Client developer: How is an optional field different from a nullable field in this interface contract?
  4. Service developer: Optional allows omission; nullable allows null. Here, omission leaves the nickname unchanged; an empty string clears it.
  5. Client developer: Then null shouldn't silently mean unchanged on one client and cleared on another.
  6. Service developer: Agreed. Shall we propose rejecting null with a validation error until another meaning is agreed?
  7. Client developer: That keeps the current clearing behavior explicit. My client can send an empty string.
  8. Service developer: Please also preserve omission for updates that don't intend to change the nickname.
  9. Client developer: I will. Those are two different user intentions, even if both look blank.
  10. Service developer: Then our proposed contract keeps both outcomes and identifies null as unsupported, pending review.
2. An empty list is a successful result

Fictional developers clarify the difference between no search matches and a failed search.

  1. Consumer developer: Our search adapter treats an empty list as an error. Is that intended?
  2. Interface owner: No. In this contract, an empty list means the search succeeded without finding matches.
  3. Consumer developer: What represents a failed request? I need to show a different message for that.
  4. Interface owner: A validation error has a separate error result. It doesn't use the successful list shape.
  5. Consumer developer: So no matches should display an empty state, while invalid input should explain the error?
  6. Interface owner: Exactly. The interface contract separates those outcomes even though neither produces visible result rows.
  7. Consumer developer: I'll remove the assumption that a successful result must contain at least one item.
  8. Interface owner: Please add the zero-match example beside the populated example when reviewing the adapter.
  9. Consumer developer: That will make the distinction concrete. We can check both without guessing from list length.
  10. Interface owner: And callers can offer another search without telling users that a successful request failed.
3. A renamed response field breaks an older caller

A fictional code review identifies a compatibility concern in a response change.

  1. Reviewer: The new response replaces displayName with label. What happens to the older caller?
  2. Developer: It still reads displayName. I changed the server response but haven't changed that client.
  3. Reviewer: Then this affects backward compatibility, not simply an internal variable name.
  4. Developer: You're right. The field crosses the interface boundary, so consumers can observe the difference.
  5. Reviewer: Do we know whether both fields could temporarily coexist under an agreed transition contract?
  6. Developer: That needs discussion with the client owner. We haven't specified precedence if values differ.
  7. Reviewer: Please keep the response change out of the internal cleanup until that contract is settled.
  8. Developer: I can separate it. The local variable rename doesn't require changing the response field.
  9. Reviewer: That gives us a focused review and keeps the existing caller's expectation intact.
  10. Developer: I'll retain displayName in this change and open the proposed interface transition for discussion.

Two scenarios to practice

Try a harder second round

Scenario 2 · A required currency without a default

A fictional pricing interface requires a currency code. A client omits it, assuming dollars. The contract supplies no default. The interface owner can confirm that omission is invalid; no conversion is involved.

Role A: Client developer: ask whether omission has a supported meaning and restate the answer.

Role B: Interface owner: explain that currency is required and a value must be supplied explicitly.

Possible opening: “Does an omitted currency mean dollars in this contract, or is it invalid?”

Success checks
  • Separate example data from the contract.
  • Confirm currency must be explicit.
  • Avoid inventing a conversion or default behavior.
Add a complication

Someone points to a dollar sign in an example and calls it a default rule.

Studying alone? Speak both roles aloud. For each scenario, prepare for two minutes, speak for one minute, then answer a follow-up. Switch roles and repeat using fewer notes. Use only the supplied facts; identify missing information instead of inventing it.

Compare scenario 1 with a model response

02Debugging from reproducible evidenceSeparate a clue from a cause · 45-60 minutes+

Your goal

Explain a debugging hypothesis and propose evidence that distinguishes it.

A Read the situation

A moment at work

A fictional import fails on a three-row file containing an empty date field. A two-row file without that row succeeds. The stack trace points to date parsing, but no controlled test has isolated the empty field as the cause.

Before you look at the model: what is confirmed, what is missing, and who needs a response?

B Find the words

Vocabulary for this lesson

reproduction
A documented set of conditions and actions that produces an observed software behavior again.
stack trace
A record of function calls associated with a point in execution, often captured when an error occurs.
hypothesis
A proposed explanation for observed behavior that can be investigated against evidence.
minimal example
A reduced input or program that retains the behavior being investigated while removing irrelevant detail.

Useful word combinations

  • reproduce a failure: make the reported behavior occur under described conditions
  • narrow the failing input: remove irrelevant detail while retaining the failure
  • inspect the call path: examine which operations led to the observed failure
  • rule out a hypothesis: use evidence to reject a proposed explanation

C Notice the language

Separate a clue from a cause

A stack trace shows a path associated with failure, not necessarily the original cause. When two examples differ in several ways, identify the confounding differences before claiming that one field explains the failure.

  • The failure occurs with ___, but ___ also differs.
  • The trace points to ___; that does not yet establish ___.
  • A comparison holding ___ constant would help distinguish ___.

Improve this: "The parser is broken because the file has an empty date."

See a clearer version

The failure reaches date parsing; the empty date is a hypothesis that still needs an isolated comparison.

The revised claim matches the evidence and names the untested explanation.

D Check your understanding

Two short language checks

These language patterns recur across courses so you can retrieve and reuse them.

1. Colleague: Does the passing two-row file prove the empty date caused the failure?
Developer: No; it also changes the ____, so that comparison does not isolate the date.

Answer and explanations

Answer: A. row count

  1. A. row count Correct. Both the date content and row count differ.
  2. B. date format No changed date format is supplied for the passing file.
  3. C. delimiter The case does not identify a changed delimiter between the files.
  4. D. character encoding No encoding difference is established in the supplied comparison.
2. Reviewer: How certain is your explanation?
Developer: The trace ____ a parsing issue, but we haven't isolated the cause.

Answer and explanations

Answer: D. suggests

  1. A. rules out Rules out rejects rather than supports the possibility.
  2. B. guarantees Guarantees overstates the trace's evidential value.
  3. C. is unrelated to Unrelated to dismisses a relevant clue.
  4. D. suggests Correct. Suggests presents a supported but unconfirmed explanation.

E Conversations

Three conversations at work

Original fictional training conversations. Each line is one speaking turn.

1. The empty date is still a hypothesis

Fictional developers discuss a failing three-row import and a passing two-row file.

  1. Developer: The three-row import fails in date parsing. I suspect the row with an empty date.
  2. Colleague: Does your passing example differ only in that date, or in other ways?
  3. Developer: It has two rows instead of three, so the comparison also changes row count.
  4. Colleague: Then it doesn't isolate the empty field. What does the stack trace actually show?
  5. Developer: The call path reaches date parsing before the failure; it doesn't establish the original cause.
  6. Colleague: Could we keep three rows and change only the disputed date in a controlled example?
  7. Developer: Yes. That would distinguish the date hypothesis from the row-count difference in these files.
  8. Colleague: Please preserve the failing input too, so another developer can reproduce the observation.
  9. Developer: I've labeled the cause unconfirmed and attached both existing examples with their differences.
  10. Colleague: Good. We have a specific hypothesis and a comparison that can test it.
2. The error line is not necessarily where the defect began

Fictional developers inspect a trace from a report formatter.

  1. Developer: The trace points to the formatter. Should we assign the whole defect there?
  2. Reviewer: Which value reached it? A failure location doesn't tell us where invalid state originated.
  3. Developer: The formatter expected a title, but the input object contains no title field.
  4. Reviewer: Does the upstream contract require that field, or may callers legitimately omit it?
  5. Developer: It requires a title. The minimal example bypasses the normal builder and leaves it out.
  6. Reviewer: Then we've identified a contract violation in the example, not yet a formatter implementation defect.
  7. Developer: That's useful. The user report may still involve a missing title from the real builder.
  8. Reviewer: Exactly. We need the actual path before deciding whether the example represents that report.
  9. Developer: I'll separate the synthetic missing-field failure from the unconfirmed production report in the discussion.
  10. Reviewer: And I'll review the builder's output contract with you rather than blame the final trace line.
3. One successful rerun doesn't establish a correction

Fictional developers discuss intermittent behavior without claiming a fix.

  1. Maintainer: The import passed on its second attempt. Can we close the failure report?

03Giving actionable code-review feedbackComment on behavior and impact · 45-60 minutes+

Your goal

Give precise review feedback that separates an acceptable edit from an unintended behavior change.

A Read the situation

A moment at work

A fictional pull request is titled 'rename export helper.' Its diff also moves a notification call outside a success branch, so failed exports would now notify the user as if complete. The naming change is acceptable; the behavior change is unintended.

Before you look at the model: what is confirmed, what is missing, and who needs a response?

B Find the words

Vocabulary for this lesson

pull request
A proposal to incorporate a set of code changes, commonly accompanied by a diff and review discussion.
diff
A representation showing added, removed, or changed content between two versions.
refactoring
Restructuring existing code while preserving its observable behavior.
side effect
An observable effect beyond a function's returned value, such as changing stored state or sending a notification.

Useful word combinations

  • keep a change focused: limit a review to a coherent behavior or purpose
  • trace a side effect: follow a change outside a function's returned value
  • separate a preference from a blocker: distinguish optional style from required correction
  • preserve existing behavior: keep observable outcomes unchanged during restructuring

C Notice the language

Comment on behavior and impact

Point to the observed change, explain the resulting behavior, and request a bounded revision. Refactoring normally preserves observable behavior; the label on a pull request does not guarantee that its diff does so.

  • The change moves ___, which means ___.
  • My concern is ___, not ___.
  • Could you preserve ___ and add evidence for ___?

Improve this: "This refactor is bad."

See a clearer version

Moving the notification outside the success branch changes the failure path; please keep it conditional on success.

The review now names the defect and a concrete revision rather than judging the author or the entire change.

D Check your understanding

Two short language checks

These language patterns recur across courses so you can retrieve and reuse them.

1. Author: Is the helper name the blocker?
Reviewer: No. The blocker is the changed ____ on failed exports.

Answer and explanations

Answer: D. side effect

  1. A. return value The review concern is the notification, not a changed returned value.
  2. B. accepted input No change to accepted input is described in this diff.
  3. C. helper signature No changed parameter or return declaration is the identified blocker.
  4. D. side effect Correct. The notification is an observable effect outside the helper's result.
2. Author: Should I redo the whole pull request?
Reviewer: The rename can stay; please ____ the notification's success condition.

Answer and explanations

Answer: C. preserve

  1. A. announce Announce communicates a condition without retaining it.
  2. B. summarize Summarize describes rather than fixes the behavior.
  3. C. preserve Correct. Preserve asks to retain the existing condition.
  4. D. infer Infer means deduce, not keep the condition in the code.

04Requesting dependency evidenceRequest the path, version, and affected call · 45-60 minutes+

Your goal

Ask for evidence that makes a dependency upgrade reviewable.

A Read the situation

A moment at work

A fictional application directly uses package ParcelKit, which brings in TextCore indirectly. A proposed ParcelKit upgrade changes the resolved TextCore version. The change note mentions a deprecated parsing entry point; the team's usage and replacement compatibility are unknown.

Before you look at the model: what is confirmed, what is missing, and who needs a response?

B Find the words

Vocabulary for this lesson

direct dependency
A component explicitly required by the application or package being discussed.
transitive dependency
A component required indirectly through another dependency in the dependency chain.
lockfile
A tool-specific record of resolved dependencies used to help reproduce a selected dependency set.
deprecation
A notice that an interface or feature is discouraged for future use, often ahead of possible removal.

Useful word combinations

  • trace the dependency path: identify which package brings another package into a build
  • review an upgrade note: examine documented changes before adopting a version
  • pin a resolved version: record a specific selected version where the tool supports it
  • check the supported interface: verify which calls remain available to consumers

C Notice the language

Request the path, version, and affected call

Direct and transitive describe how a dependency enters the application. Deprecation warns that an interface should be replaced or may be removed; it does not by itself establish removal now. Tool and package behavior must be checked in their actual documentation.

  • Which dependency introduces ___?
  • Could you link the change note and identify our use of ___?
  • Does the resolved version change from ___ to ___?

Improve this: "It's a small version change, so it won't affect us."

See a clearer version

Please show the resolved dependency change and check whether our callers use the deprecated entry point.

The revision requests evidence rather than treating a version label as a compatibility guarantee.

D Check your understanding

Two short language checks

These language patterns recur across courses so you can retrieve and reuse them.

1. Reviewer: We don't list TextCore directly. How does it enter the build?
Developer: For our application, TextCore is a ____ dependency introduced by ParcelKit.

Answer and explanations

Answer: C. transitive

  1. A. optional Optional concerns whether it is required, not the stated dependency path.
  2. B. development-only Development-only concerns its usage scope, not how it enters the application.
  3. C. transitive Correct. The application receives it through another dependency.
  4. D. direct The application does not list it directly; ParcelKit introduces it.
2. Developer: The note says deprecated. Does that prove the entry point is absent now?
Reviewer: No; deprecation and ____ are different states.

Answer and explanations

Answer: B. removal

  1. A. resolution Resolution selects dependencies and is not the opposite availability state.
  2. B. removal Correct. An interface may be deprecated before removal.
  3. C. documentation Documentation is the evidence source, not the contrasting availability state.
  4. D. installation Installation does not express that the entry point no longer exists.

Your goal

Explain why repeating a state-changing request needs an explicit behavior contract.

A Read the situation

A moment at work

A fictional reservation client times out before receiving a reply. The reservation may already have been created. A colleague proposes automatically submitting a second request as a new reservation. The service's duplicate-request behavior is unspecified; no production change is authorized.

Before you look at the model: what is confirmed, what is missing, and who needs a response?

B Find the words

Vocabulary for this lesson

race condition
Behavior whose outcome depends on the timing or ordering of overlapping operations.
idempotency
The property that repeating an operation has the same intended effect as performing it once.
transaction
A defined unit of related work whose completion and consistency guarantees depend on the system's transaction model.
invariant
A condition that the design requires to remain true across relevant operations or state changes.

Useful word combinations

  • retry an operation: attempt it again after an uncertain or failed result
  • preserve an invariant: maintain a condition that must remain true
  • separate acknowledgment from completion: distinguish a received reply from the underlying outcome
  • interleave two requests: describe overlapping operations whose steps may occur in mixed order

C Notice the language

Challenge an assumption about an uncertain outcome

A client may fail to receive a reply even when a service completed work. Idempotency concerns the intended effect of repetition, not a promise that every response or timing is identical. Discuss the fictional contract rather than prescribing a production retry mechanism.

  • A missing reply does not establish that ___.
  • If the first request completed, a new request could ___.
  • Before retrying, we need agreement on ___.

Improve this: "It timed out, so nothing happened."

See a clearer version

The client timed out; the reservation outcome is unknown. Repeating it as a new request could have another effect.

The revision separates the client's observation from the service's unconfirmed state.

08Handing over a release with explicit limitsTransfer deployment, exposure, and compatibility status · 45-60 minutes+

Your goal

Give a release handover that distinguishes installed software from enabled behavior and verified recovery.

A Read the situation

A moment at work

Fictional build R18 is deployed to staging. Its new search view is disabled by a feature flag. A schema migration adds an optional field, but compatibility with the previous application build is untested. Lee takes the release review; production rollout is undecided.

Before you look at the model: what is confirmed, what is missing, and who needs a response?

B Find the words

Vocabulary for this lesson

build artifact
A generated software output, such as a package or executable, produced from a particular build.
feature flag
A control that enables, disables, or varies specified application behavior without necessarily changing the deployed build.
rollback
A return to an earlier application or configuration state, whose scope may not include undoing data changes.
schema migration
A controlled change to the structure or organization of stored data.

Useful word combinations

  • identify the deployed build: name the exact software output running in an environment
  • stage a rollout: expose a change in bounded steps
  • define a rollback limit: explain what reverting the application does not undo
  • hand over an open compatibility check: transfer responsibility for an unresolved interaction

C Notice the language

Transfer deployment, exposure, and compatibility status

A deployed artifact may contain disabled behavior. Rolling back an application does not automatically undo data changes. State which environment and build were checked and name the remaining review without promising recovery.

  • Build ___ is deployed to ___; the feature is ___.
  • The data change is ___, while compatibility with ___ is ___.
  • Please confirm ownership of ___ before the release decision.

Improve this: "R18 is live and rollback is fine."

See a clearer version

R18 is in staging with search disabled; previous-build compatibility with the changed schema remains untested.

The revision avoids conflating staging deployment, feature exposure, and verified rollback.

D Check your understanding

Two short language checks

These language patterns recur across courses so you can retrieve and reuse them.

1. Release reviewer: Can staging users access the new search view?
Developer: Not through the flag-controlled route; the feature flag is ____.

Answer and explanations

Answer: C. disabled

  1. A. enabled for a pilot group No pilot exposure is enabled in the supplied staging state.
  2. B. removed from the build The feature exists in the build; its exposure is disabled rather than removed.
  3. C. disabled Correct. The case states that exposure is disabled.
  4. D. enabled for everyone The flag is disabled, so universal exposure is not supported.
2. Lee: Does reverting the application prove the schema change is undone?
Developer: No. Application rollback and schema reversal are ____.

Answer and explanations

Answer: B. separate concerns

  1. A. matching artifacts Artifacts are build outputs, not the relationship between these actions.
  2. B. separate concerns Correct. Reverting application code does not itself establish a data reversal.
  3. C. identical guarantees They are not interchangeable guarantees.
  4. D. completed checks Neither action is reported as checked here.
